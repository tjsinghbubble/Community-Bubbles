How to move Bubble to a Linode test host

A command-by-command weekend runbook. Written 2026-07-18 · companion to Move-from-Replit.md · performance/cost testing continues in How-to-test-on-Linode.md

What this runbook does. It stands up a complete, working copy of Bubble (application, database, stand-in photo storage, HTTPS) on a rented Linode server, under your own domain — it never touches trybubble.io, its DNS, or the live Replit deployment. Everything is disposable: the final section deletes it all.

Cost: the server bills hourly at $0.036/hr — a full weekend ≈ $2.60, plus your test domain (~$10–15/yr if you register a new one). Time: roughly 2–3 hours of hands-on work, plus DNS and upload waiting.
How to read the commands. Each command block is labeled with your mac (run in a local terminal, from the Bubble/ repo directory unless said otherwise) or server (run inside an SSH session on the Linode), and with its purpose: forward moves the migration ahead, check verifies status and changes nothing, rollback undoes the step, and enable/disable pauses or resumes without destroying anything. Checkboxes remember themselves in this browser. (Stored locally only.)

Phase 0 — Prepare your Mac

your macforwardInstall and configure the Linode command-line tool (paste your token when prompted; pick region us-east)
brew install linode-cli
linode-cli configure
your maccheckConfirm the CLI works and you have an SSH key
linode-cli account view --text
ls ~/.ssh/id_ed25519.pub || ssh-keygen -t ed25519

Set the working variables for this whole runbook. Every later command assumes these are set in your current terminal — re-paste this block in any new terminal window (and fill in the values you learn as you go).

your macforwardSession variables — edit the first two lines, then paste the whole block
export BUBBLE_DOMAIN="yourdomain.example"        # the domain YOU control (Phase 1)
export BUBBLE_HOST="bubble.$BUBBLE_DOMAIN"       # the test site's full address
export BUBBLE_IP=""                              # filled in after Phase 2
export PG_PASS="$(openssl rand -hex 16)"; echo "PG_PASS=$PG_PASS  (save this)"

Phase 1 — Pick and register the test domain

This runbook assumes a domain you personally control (you do not have control of trybubble.io, and this test must not touch it). Any registrar works — Cloudflare Registrar and Porkbun are cheap and sane. You only need one A-record, so nothing fancy.

A non-exhaustive registration check centered on Boudicca, Boudicca Software, and variant spellings, via the public RDAP registry service. Heads-up on .dev and .app: both force HTTPS in every browser (no plain-HTTP fallback while you debug). Phase 2 — Create the server

One "Linode 4GB" shared server (2 CPUs, 4 GB memory — the size all the research sizing points at), in Newark, running Ubuntu 24.04, with your SSH key installed from the start.

your macforwardCreate the server (root password is required by Linode; make it long and random — you'll never type it)
linode-cli linodes create \
  --label bubble-test \
  --region us-east \
  --type g6-standard-2 \
  --image linode/ubuntu24.04 \
  --root_pass "$(openssl rand -base64 24)" \
  --authorized_keys "$(cat ~/.ssh/id_ed25519.pub)" \
  --text
your maccheckWatch it boot (status becomes running in ~1 minute) and capture its address into $BUBBLE_IP
linode-cli linodes list --label bubble-test --text
export BUBBLE_IP=$(linode-cli linodes list --label bubble-test --format ipv4 --text --no-headers)
echo "BUBBLE_IP=$BUBBLE_IP"
your maccheckFirst login (accept the host key)
ssh root@$BUBBLE_IP 'hostname; uptime'
your macrollbackUndo this phase — destroy the server (stops all billing for it)
linode-cli linodes delete $(linode-cli linodes list --label bubble-test --format id --text --no-headers)

Phase 3 — Lock it down

Two layers, both free: Linode's Cloud Firewall in front of the machine (only SSH and the two web ports may pass), and on the machine, key-only SSH plus fail2ban to ban brute-forcers.

your macforwardCreate the firewall (default-deny inbound; allow only 22, 80, 443) and attach it to the server
linode-cli firewalls create --label bubble-fw \
  --rules.inbound_policy DROP --rules.outbound_policy ACCEPT \
  --rules.inbound '[
    {"label":"ssh","action":"ACCEPT","protocol":"TCP","ports":"22","addresses":{"ipv4":["0.0.0.0/0"],"ipv6":["::/0"]}},
    {"label":"http","action":"ACCEPT","protocol":"TCP","ports":"80","addresses":{"ipv4":["0.0.0.0/0"],"ipv6":["::/0"]}},
    {"label":"https","action":"ACCEPT","protocol":"TCP","ports":"443","addresses":{"ipv4":["0.0.0.0/0"],"ipv6":["::/0"]}}
  ]' --text
FW_ID=$(linode-cli firewalls list --label bubble-fw --format id --text --no-headers)
LINODE_ID=$(linode-cli linodes list --label bubble-test --format id --text --no-headers)
linode-cli firewalls device-create $FW_ID --id $LINODE_ID --type linode --text
If you know your home IP is stable, tighten SSH by replacing "0.0.0.0/0" in the ssh rule with "<your-ip>/32". Skippable for a weekend test — fail2ban below covers the noise.
serverforwardKey-only SSH + fail2ban (run inside ssh root@$BUBBLE_IP)
printf 'PasswordAuthentication no\nPermitRootLogin prohibit-password\n' > /etc/ssh/sshd_config.d/90-bubble.conf
systemctl reload ssh
apt-get update && apt-get install -y fail2ban
systemctl enable --now fail2ban
your maccheckConfirm: password auth refused, firewall attached
ssh -o PubkeyAuthentication=no -o PasswordAuthentication=yes root@$BUBBLE_IP true 2>&1 | tail -1   # expect: Permission denied
linode-cli firewalls list --text

Phase 4 — Point DNS at the server

Two routes — pick one. Route A (recommended for the weekend): add one record at your registrar's own DNS panel: an A record, name bubble, value $BUBBLE_IP, TTL 300. Done — skip to the check below. Route B: host the zone at Linode so everything lives in one CLI (requires switching your domain's nameservers at the registrar to ns1–ns5.linode.com, which can take hours to propagate — do it Friday, not Saturday night).

your macforwardRoute B only — create the zone and the record at Linode
linode-cli domains create --type master --domain "$BUBBLE_DOMAIN" --soa_email "travis.winfrey@gmail.com" --text
DOMAIN_ID=$(linode-cli domains list --domain "$BUBBLE_DOMAIN" --format id --text --no-headers)
linode-cli domains records-create $DOMAIN_ID --type A --name bubble --target "$BUBBLE_IP" --ttl_sec 300 --text
# then, at your registrar: set nameservers to ns1.linode.com ... ns5.linode.com
your maccheckConfirm the name resolves to your server (repeat until it does; TTL 300 = re-check every 5 min)
dig +short $BUBBLE_HOST @1.1.1.1
echo "should print: $BUBBLE_IP"
your macrollbackUndo — delete the record (Route A: delete it in the registrar panel)
DOMAIN_ID=$(linode-cli domains list --domain "$BUBBLE_DOMAIN" --format id --text --no-headers)
linode-cli domains records-list $DOMAIN_ID --text
linode-cli domains records-delete $DOMAIN_ID <record-id>
No domain yet / DNS not propagating? You can proceed with a zero-setup fallback name: export BUBBLE_HOST="$(echo $BUBBLE_IP | tr . -).sslip.io" — a public convenience service that resolves that name to your IP automatically. Fine for a weekend test; use your real domain for anything you show to others.

Phase 5 — Install Docker and Caddy on the server

serverforwardDocker (official convenience installer) + Caddy (official apt repo)
curl -fsSL https://get.docker.com | sh
apt-get install -y debian-keyring debian-archive-keyring apt-transport-https
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/gpg.key' | gpg --dearmor -o /usr/share/keyrings/caddy-stable-archive-keyring.gpg
curl -1sLf 'https://dl.cloudsmith.io/public/caddy/stable/debian.deb.txt' > /etc/apt/sources.list.d/caddy-stable.list
apt-get update && apt-get install -y caddy
servercheckConfirm both installed and running
docker --version && docker compose version
systemctl is-active caddy

Phase 6 — Build the app container locally and ship it up

The container is built on your Mac with the existing research build script (already proven in the load tests), then copied to the server over SSH. The compressed image is a few hundred MB — expect 10–30 minutes depending on your uplink; start it and get coffee.

your macforwardBuild the image (from the Bubble/ repo directory)
scripts/one-off/hosting-docker-build.sh
your macforwardShip it to the server
docker save bubble-api:research | gzip | ssh root@$BUBBLE_IP 'gunzip | docker load'
your maccheckConfirm the image arrived
ssh root@$BUBBLE_IP docker images

Phase 7 — Configure and start the stack

Three containers on the server, same shape as the local experiment stack: the app, PostgreSQL 16, and a stand-in photo store (the documented no-code-change workaround for the Replit storage coupling — see the plan's §"one real obstacle"). All of them listen only on the server's loopback; the outside world reaches the app solely through Caddy (Phase 9).

serverforwardCreate the deployment directory and compose file
mkdir -p /opt/bubble && cd /opt/bubble
cat > compose.yaml <<'EOF'
name: bubble
services:
  db:
    image: postgres:16
    restart: unless-stopped
    environment:
      POSTGRES_USER: bubble
      POSTGRES_PASSWORD: ${PG_PASS}
      POSTGRES_DB: bubble
    volumes: [ bubble_pgdata:/var/lib/postgresql/data ]
    ports: [ "127.0.0.1:5433:5432" ]     # loopback only — for the SSH-tunnel schema/seed step
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U bubble -d bubble"]
      interval: 5s
      timeout: 3s
      retries: 12
  gcs:
    image: fsouza/fake-gcs-server:latest
    restart: unless-stopped
    command: ["-scheme", "http", "-port", "4443", "-public-host", "gcs:4443"]
  api:
    image: bubble-api:research
    restart: unless-stopped
    depends_on:
      db: { condition: service_healthy }
      gcs: { condition: service_started }
    env_file: [ .env ]
    environment:
      DATABASE_URL: postgres://bubble:${PG_PASS}@db:5432/bubble
      STORAGE_EMULATOR_HOST: http://gcs:4443
      PORT: "5000"
    ports: [ "127.0.0.1:5000:5000" ]     # loopback only — Caddy is the front door
volumes:
  bubble_pgdata:
EOF
serverforwardCreate the secrets file with FRESH secrets (never reuse Replit's — they are visible to every Replit collaborator). Fill in the CometChat values from the team vault if you want chat to work; leave them blank otherwise and everything else still runs.
cd /opt/bubble
cat > .env <<EOF
JWT_SECRET=$(openssl rand -hex 32)
ENCRYPTION_KEY=$(openssl rand -hex 32)
EXPO_PUBLIC_COMETCHAT_APP_ID=
EXPO_PUBLIC_COMETCHAT_REGION=us
COMETCHAT_AUTH_KEY=
COMETCHAT_API_KEY=
PRIVATE_OBJECT_DIR=/bubble-local/private
PUBLIC_OBJECT_SEARCH_PATHS=/bubble-local/public
EOF
chmod 600 .env
echo "PG_PASS=<paste the PG_PASS value from your Mac>" > .pgpass.env   # then edit it for real
chmod 600 .pgpass.env
Edit /opt/bubble/.pgpass.env so it contains the actual PG_PASS=… value you generated in Phase 0 (it's the database password both sides must agree on). Then start the stack with that value loaded:
serverforwardStart everything
cd /opt/bubble && set -a && . ./.pgpass.env && set +a
docker compose up -d
servercheckStatus and logs — the API will complain about a missing schema until Phase 8; that's expected
docker compose ps
docker compose logs --tail 50 api
serverrollbackUndo — stop and remove containers (add -v to also erase the database volume for a truly clean slate)
cd /opt/bubble && docker compose down        # or: docker compose down -v

Phase 8 — Create the database schema and seed test data

A brand-new database has no tables — the app's boot-time migrator only patches, it doesn't bootstrap (a documented gotcha). You run the one-time schema push from your Mac, through an SSH tunnel to the server's loopback-only database port, using the repo's own tooling. Same tunnel seeds the test accounts.

your macforwardOpen the tunnel (leave this running in its own terminal; Ctrl-C closes it)
ssh -N -L 5433:127.0.0.1:5433 root@$BUBBLE_IP
your macforwardIn a second terminal (with Phase 0 variables set, from Bubble/): create the schema, seed test data, restart the app
export TUNNEL_DB="postgres://bubble:$PG_PASS@127.0.0.1:5433/bubble"
DATABASE_URL="$TUNNEL_DB" npx drizzle-kit push --force
DATABASE_URL="$TUNNEL_DB" npx tsx scripts/seed-test-data.ts
ssh root@$BUBBLE_IP 'cd /opt/bubble && set -a && . ./.pgpass.env && set +a && docker compose restart api'
your maccheckThe app should now answer on the server's loopback
ssh root@$BUBBLE_IP 'curl -fsS http://127.0.0.1:5000/api/v1/ping && echo OK'

Phase 9 — Turn on HTTPS

Caddy fetches and renews a free certificate automatically the moment its config names your domain — provided Phase 4's DNS record already points here (the certificate authority checks).

serverforwardPoint Caddy at the app — replace BUBBLE_HOST_HERE with your actual host name (e.g. bubble.boudicca.io)
cat > /etc/caddy/Caddyfile <<'EOF'
BUBBLE_HOST_HERE {
    reverse_proxy 127.0.0.1:5000
}
EOF
sed -i "s/BUBBLE_HOST_HERE/bubble.yourdomain.example/" /etc/caddy/Caddyfile   # <-- edit me
systemctl reload caddy
your maccheckThe site is live on the real internet
curl -fsS https://$BUBBLE_HOST/api/v1/ping && echo && echo "OPEN IN BROWSER: https://$BUBBLE_HOST"
serverrollbackUndo — take the site off the internet (containers keep running privately)
systemctl stop caddy

Phase 10 — Verify the deployment

your maccheckThe safe production-mode probes (from the plan's appendix A.6 — these can never crash a server)
curl -fsS https://$BUBBLE_HOST/api/v1/ping ; echo
curl -fsS https://$BUBBLE_HOST/api/v1/version ; echo
curl -fsS https://$BUBBLE_HOST/ | grep -o '/assets/index-[^"]*\.js' | head -1   # hashed asset => production mode
curl -fsS https://$BUBBLE_HOST/ | grep -c '@vite/client'                        # MUST print 0

Phase 11 — Build the mobile app against the test site

The phone app learns its server address at build time from EXPO_PUBLIC_API_URL — the released app is pinned to trybubble.io, so testing the Linode site needs its own build with the variable overridden. Two paths:

Path A — simulator/emulator dev build (recommended for the weekend)

With a dev build, the JavaScript is served by Metro on your Mac, so the override must be set on both the build and the Metro process. Note: per current Apple team roles, only simulator builds are possible from this machine (no device signing) — the iOS simulator and Android emulator are exactly what this weekend needs anyway.
your macforwardiOS simulator build + Metro, both pointed at the test site (two terminals)
# terminal 1 — build & install to the simulator
EXPO_PUBLIC_API_URL="https://$BUBBLE_HOST" npm run mobile:build:ios-sim

# terminal 2 — Metro, with the same override
EXPO_PUBLIC_API_URL="https://$BUBBLE_HOST" npm run metro_bundler
your macforwardAndroid emulator equivalent
cd mobile && EXPO_PUBLIC_API_URL="https://$BUBBLE_HOST" npx expo run:android
your maccheckConfirm the app is really talking to Linode, not Replit — watch the test server's live request log while tapping around the app
ssh root@$BUBBLE_IP 'cd /opt/bubble && docker compose logs -f --tail 5 api'

Path B — a shareable standalone build (only if others must install it)

Add a copy of the preview profile to mobile/eas.json named linode-test, with "EXPO_PUBLIC_API_URL": "https://bubble.<your-domain>" in its env block, then eas build --profile linode-test. This spends EAS build credits and needs store-signing roles — defer it unless genuinely needed.

Two known limits of the test build: tap-a-link-opens-the-app ("universal links") won't trigger for your test domain — the association file and the app's entitlements are tied to trybubble.io; test links in the browser instead. And chat stays dead unless you filled in the CometChat keys in Phase 7.

Phase 12 — Optional: rehearse with a copy of real data

Think before doing this. Copying production data puts real users' information on a weekend test box. Only proceed after Phases 3 and 9 are verified (firewall, key-only SSH, HTTPS), keep the copy's lifetime short, and delete the server (Phase 13) when done — don't let it linger. The seeded test data is enough for almost everything this weekend is for.
your macforwardDump production (needs the Replit database URL from the team vault) and restore through the Phase-8 tunnel
pg_dump --no-owner --no-privileges -Fc "$REPLIT_DATABASE_URL" -f /tmp/bubble-prod.dump
pg_restore --no-owner --clean --if-exists -d "postgres://bubble:$PG_PASS@127.0.0.1:5433/bubble" /tmp/bubble-prod.dump
ssh root@$BUBBLE_IP 'cd /opt/bubble && set -a && . ./.pgpass.env && set +a && docker compose restart api'
rm /tmp/bubble-prod.dump
your macrollbackUndo — wipe the copied data entirely and re-seed fresh test data (Phase 8)
ssh root@$BUBBLE_IP 'cd /opt/bubble && set -a && . ./.pgpass.env && set +a && docker compose down -v && docker compose up -d'

Phase 13 — Pause, resume, and full teardown

serverdisablePause the site (keeps all data; frees nothing on the bill)
systemctl stop caddy
cd /opt/bubble && docker compose stop
serverenableResume the site
cd /opt/bubble && set -a && . ./.pgpass.env && set +a && docker compose start
systemctl start caddy
Billing truth: Linode charges for a server even while it is powered off — the hardware stays reserved. linode-cli linodes shutdown does not stop the meter; only deleting the server does. At $0.036/hr an idle week is about $6 — not ruinous, but don't assume "off" means "free."
your macrollbackFull teardown — destroys the server, its data, the firewall, and (Route B) the DNS zone. Billing stops. This is the "leave no trace" button.
linode-cli linodes delete $(linode-cli linodes list --label bubble-test --format id --text --no-headers)
linode-cli firewalls delete $(linode-cli firewalls list --label bubble-fw --format id --text --no-headers)
# Route B only:
# linode-cli domains delete $(linode-cli domains list --domain "$BUBBLE_DOMAIN" --format id --text --no-headers)
# Route A: also delete the A record in your registrar panel.

Phase 14 — What this weekend deliberately does not cover

This runbook proves the move works. A production cutover adds, per the main report and the deployment plan:

  • Linode's managed PostgreSQL (daily backups + point-in-time recovery) instead of the database container — this is the whole point of the move.
  • Real photo storage instead of the stand-in: the small code change (option 3 in the plan) or the credential shim, plus migrating existing photos.
  • The trybubble.io DNS cutover — owned by whoever controls that zone, with lowered TTL, a dual-run rehearsal on real data, and Replit kept warm for 1–2 weeks of instant rollback.
  • Rotation of every secret in Replit's shared configuration, on a coordinated schedule.
  • A rehearsed, timed database-restore drill, monitoring/alerting, and unattended OS security updates.
